## 一、关系模式转换

### 1. 用户表（users）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| user_id | INTEGER | **PRIMARY KEY**，自增 | 用户唯一ID |
| username | VARCHAR(50) | **UNIQUE NOT NULL** | 登录名 |
| password_hash | VARCHAR(255) | NOT NULL | 密码哈希值 |
| created_at | TIMESTAMP | NOT NULL DEFAULT CURRENT_TIMESTAMP | 注册时间 |

- **范式分析**：只有一个候选键 `user_id`，所有非主属性都完全函数依赖于 `user_id`，不存在传递依赖，满足3NF。决定因素 `user_id` 包含候选键，符合BCNF。

### 2. 族谱表（genealogies）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| genealogy_id | INTEGER | **PRIMARY KEY**，自增 | 族谱唯一ID |
| name | VARCHAR(100) | NOT NULL | 谱名 |
| surname | VARCHAR(50) | NOT NULL | 姓氏 |
| compile_time | DATE | | 修谱时间 |
| description | TEXT | | 简介 |
| creator_id | INTEGER | **NOT NULL** REFERENCES users(user_id) | 创建者 |

- **范式分析**：`genealogy_id` 为主键，所有属性直接依赖于它，`creator_id` 不是传递依赖（它是外键，但本身是非码属性），不违反3NF。符合BCNF。

### 3. 用户-族谱协作表（user_genealogy）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| user_id | INTEGER | **NOT NULL** REFERENCES users(user_id) | 用户ID |
| genealogy_id | INTEGER | **NOT NULL** REFERENCES genealogies(genealogy_id) | 族谱ID |
| role | VARCHAR(20) | NOT NULL DEFAULT 'editor' | 角色（creator/editor） |
| joined_at | TIMESTAMP | NOT NULL DEFAULT CURRENT_TIMESTAMP | 加入时间 |
|  |  | **PRIMARY KEY (user_id, genealogy_id)** |  |

- **范式分析**：联合主键 `(user_id, genealogy_id)`，`role` 和 `joined_at` 对主键完全函数依赖，无传递依赖，满足3NF。决定因素只可能是主键，满足BCNF。

### 4. 成员表（persons）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| person_id | INTEGER | **PRIMARY KEY**，自增 | 成员唯一ID |
| name | VARCHAR(100) | NOT NULL | 姓名 |
| gender | CHAR(1) | NOT NULL CHECK (gender IN ('M', 'F')) | 性别 |
| birth_year | INTEGER | | 出生年份 |
| death_year | INTEGER | | 卒年，NULL 表示在世 |
| biography | TEXT | | 生平简介 |
| generation | INTEGER | NOT NULL | 辈分，族谱始祖为1 |
| genealogy_id | INTEGER | **NOT NULL** REFERENCES genealogies(genealogy_id) | 所属族谱 |
| birth_family_id | INTEGER | REFERENCES families(family_id) | 出生家庭，NULL表示未知 |

- **附加 CHECK 约束**：`birth_year > 0`，`death_year IS NULL OR death_year >= birth_year`（保证卒年不小于出生年）。
- **范式分析**：主键 `person_id`，非主属性完全函数依赖于此。`generation` 虽可由 `birth_family_id` 递归得出，但它作为冗余属性直接依赖于 `person_id`（每个成员都有一个辈分），不构成传递依赖（没有通过其他非码属性依赖主键）。整表满足3NF。决定因素只有主键候选，满足BCNF。

**确保同名不同辈分的需求**：此处不要求姓名唯一，同一个族谱中可能出现同名人，可以通过 `person_id`、`generation` 和出生年份区分。

### 5. 家庭表（families）

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| family_id | INTEGER | **PRIMARY KEY**，自增 | 家庭ID |
| husband_id | INTEGER | REFERENCES persons(person_id) | 丈夫，可空（单亲） |
| wife_id | INTEGER | REFERENCES persons(person_id) | 妻子，可空 |
| genealogy_id | INTEGER | **NOT NULL** REFERENCES genealogies(genealogy_id) | 所属族谱 |
| marriage_year | INTEGER | | 结婚年份，可选 |
|  |  | CHECK (husband_id IS NOT NULL OR wife_id IS NOT NULL) | 至少双亲中有一个存在 |
|  |  | CHECK (husband_id <> wife_id) | 丈夫和妻子不能是同一个人 |

- **范式分析**：主键 `family_id`，其他属性完全函数依赖，满足3NF。决定因素只有主键，满足BCNF。

**家庭与成员的关联**：
- 一个家庭最多有一个丈夫和一个妻子，分别通过 `husband_id` 和 `wife_id` 引用 `persons`。
- 子女通过 `persons.birth_family_id` 指向其出生家庭，从而与父母关联。
- 这种设计避免了单独的 `parent_child` 表，简化了向上递归（子女→家庭→父母），同时满足3NF。

## 二、跨表约束（业务规则）设计

某些约束无法通过简单的 CHECK 实现，因为它们涉及多张表，需要触发器来保证数据完整性。

### 1. 父亲的出生年份必须早于子女

**规则**：对于任何 `persons` 表中的成员，如果 `birth_family_id` 不为空，则其出生年份必须晚于其父亲的出生年份（如果父亲存在），也晚于母亲的出生年份（如果母亲存在）。

**实现思路**：在 `persons` 表上创建 BEFORE INSERT OR UPDATE 触发器，通过 `birth_family_id` 找到相应的 `families` 行，再取 `husband_id` 和 `wife_id` 的出生年份进行比较。

### 2. 同一个人不能同时作为一个家庭中的丈夫和妻子

已通过 `CHECK (husband_id <> wife_id)` 保证，但该约束只针对同一行。触发器还可进一步保证丈夫和妻子不是同一个人的情况，但 CHECK 已足够。

### 3. 辈分（generation）的自动维护

为了确保数据一致性，可以在 `persons` 表上建立触发器：当插入或更新 `birth_family_id` 时，自动计算 `generation`。计算逻辑为：
- 如果 `birth_family_id` 为 NULL，则 `generation = 1`（始祖）或由应用指定。
- 否则，取父亲的 `generation + 1`（或母亲，取决于辈分从哪边计算，通常取父亲的代数）。假设族谱以男性为主线，母亲与父亲同辈分。
- 我们也允许手动设置，但触发器可用来自动纠正。

### 4. 性别与家庭角色的一致性（可选）

确保家庭表中 `husband_id` 对应的必须是男性，`wife_id` 对应的必须是女性。可通过 CHECK 约束结合子查询，但 CHECK 中不能直接跨表，需用触发器。

## 三、索引设计概要（为后续物理设计铺垫）

尽管物理优化是第五阶段的内容，但为了完整性，这里先列出将来必须建立的索引：

- `persons(genealogy_id, generation)` 复合索引 → 加速同族谱按辈分统计。
- `persons(birth_family_id)` → 加速向下递归（查找某家庭的所有子女）。
- `persons(name)` 或使用 `pg_trgm` 的 GIN 索引 → 支持模糊查询。
- `families(husband_id)` 和 `families(wife_id)` → 快速找到某人的配偶家庭。
- `users(username)` 唯一索引 → 由 UNIQUE 约束自动创建。
- `user_genealogy` 中两个外键列的索引 → 由主键自动覆盖？主键为 (user_id, genealogy_id)，查询某用户的族谱时只用到 user_id，单独建一个 `(user_id)` 索引会更好。可以采用复合主键并将 `user_id` 放在前面，这样主键索引本身就能用于 `WHERE user_id = ?`。

## 四、范式总结

所有五个表均满足第三范式（3NF）：
- 每个表的非主属性都完全函数依赖于候选键，没有传递依赖。
- `persons.generation` 虽然可由其他属性推导，但仍然直接依赖于 `person_id`，不是传递依赖（传递依赖要求非主属性依赖于另一个非主属性，再通过该非主属性依赖于主键）。这里只存在 `person_id → generation` 的函数依赖，不违反3NF。

更进一步，所有表都满足 BCNF：唯一决定因素是码（主键），不存在非主属性决定主键的情况。
