### 第二阶段：需求分析与概念设计（ER图）

**3. 分析实体与联系**  
关键概念：  
- 用户（User）：注册登录，创建或受邀族谱。  
- 族谱（Genealogy）：谱名、姓氏、修谱时间、创建者。  
- 成员（Person）：姓名、性别、生卒年、生平简介。  
- 关系（Relationship）：表示成员间的血缘或婚姻联系。  
- 注意：父子/父女、母子/母女是血缘关系；婚姻关系需单独记录。  

根据需求，梳理实体：  
- **User** (user_id, username, password, ...)  
- **Genealogy** (genealogy_id, name, surname, compile_time, creator_id)  
- **Person** (person_id, name, gender, birth_year, death_year, biography, genealogy_id)  
- **Family** (family_id, husband_id, wife_id, genealogy_id) —— 婚姻关系实体，一个家庭包含夫妻。  
- **Parent_Child** (family_id, child_id) —— 子女关系，子女在某个家庭中出生。  

思考为何这样设计：  
- 现实中的血缘关系建立在“家庭”之上，孩子属于一个父母家庭，可支持一夫多妻（多个家庭）。  
- 直接只做父子/母子关系不灵活，通过家庭关联父母与子女，查询时关联即可。  

**4. 绘制ER图**  
- 工具可用 Draw.io、Visio、PowerDesigner 或手绘后拍照。  
- 实体用矩形，属性用椭圆，联系用菱形。  
- 标示联系：User 与 Genealogy 为 1:N（一个用户创建多个族谱，族谱属于一个创建者）；Genealogy 与 Person 为 1:N；Person 与 Family 通过 husband_id/wife_id 关联；Family 与 Parent_Child 为 1:N。  
- 还需要一个“族谱共享”关系实现用户邀请：User 与 Genealogy 的 M:N 联系，通过表 **User_Genealogy** 实现（记录 user_id, genealogy_id, role）。

### 第三阶段：逻辑设计与规范化（3NF/BCNF）

**5. 转换关系模式（表结构）**  
在 ER 图基础上，定义表如下（以 MySQL 为例）：

- **user** (user_id INT PRIMARY KEY AUTO_INCREMENT, username VARCHAR(50) UNIQUE, password_hash VARCHAR(255), ...)  
- **genealogy** (genealogy_id INT PK AUTO_INCREMENT, name VARCHAR(100), surname VARCHAR(50), compile_time DATE, creator_id INT REFERENCES user(user_id))  
- **user_genealogy** (user_id INT, genealogy_id INT, role ENUM('creator','editor'), PRIMARY KEY(user_id, genealogy_id), FOREIGN KEY user_id REFERENCES user, FOREIGN KEY genealogy_id REFERENCES genealogy)  
- **person** (person_id INT PK AUTO_INCREMENT, name VARCHAR(100), gender ENUM('M','F'), birth_year INT, death_year INT, biography TEXT, genealogy_id INT REFERENCES genealogy, generation INT) —— generation 表示辈分，根为1，子+1。  
- **family** (family_id INT PK AUTO_INCREMENT, husband_id INT, wife_id INT, genealogy_id INT, FOREIGN KEY husband_id REFERENCES person, FOREIGN KEY wife_id REFERENCES person, FOREIGN KEY genealogy_id REFERENCES genealogy)  
- **parent_child** (family_id INT, child_id INT, PRIMARY KEY(family_id, child_id), FOREIGN KEY family_id REFERENCES family, FOREIGN KEY child_id REFERENCES person)  

**为何添加 generation 字段？** 虽然可以通过父子关系递归计算，但预先存储辈分能加速统计查询（如“平均寿命最长的一代”）。可以通过数据生成时计算，或在插入时根据父代辈分+1自动维护。

**6. 范式分析**  
- 所有表满足 1NF（属性原子化，无重复组）。  
- 没有部分函数依赖（主键都是单列或联合主键，联合主键没有部分依赖），满足 2NF。  
- 不存在传递依赖（非主属性只依赖于主键），因此满足 3NF。  
- 检查 BCNF：每个决定因素都包含候选键。在 parent_child 表，{family_id, child_id} 是主键，无其他决定因素；family 表只有 family_id 是候选键，其他列依赖它，满足 BCNF。  

**7. 定义约束**  
- 主键如上述。  
- 外键：所有引用字段。  
- CHECK 约束（MySQL 8.0.16+ 支持 CHECK，否则用触发器）：  
  - `birth_year < death_year`（如果 death_year 不为 null）。  
  - 父亲的出生年份 < 子女出生年份（需要在父表和子表间用触发器实现，因为 CHECK 不能跨表）。  
  - 性别只能是 'M'/'F'。  
- 唯一约束：(genealogy_id, name, generation) 也许需要唯一，但同名同姓不同辈分允许，所以不设置姓名的唯一约束，只靠 person_id 区分。

**9. 索引设计**  
- 为 `person(name)` 创建前缀索引或全文索引以支持模糊查询（LIKE '%name%' 前缀索引无效，需 FULLTEXT 索引或外部搜索引擎；但可建普通 BTREE 索引加速 `WHERE name LIKE '张%'`，如果要求模糊查找仅支持前缀匹配）。根据要求“人名的模糊查找”，可以设计：MySQL 中可建立 FULLTEXT INDEX 在 name 上，或使用 `LIKE '%keyword%'`，简单的做法是建普通索引并接受全表扫描命中率不高，但演示时可说明。  
- 为 `parent_child(child_id)` 和 `parent_child(family_id)` 创建索引，支持“根据父节点 ID 查询子节点”（需要先通过 family 表找到 husband/wife 对应的 family_id，再查 child）。实际更方便是为 `person` 表的 `genealogy_id` 建索引。  
- 为 `family(husband_id)`、`family(wife_id)` 建索引，用于快速查找某人的配偶家庭。  
- 为 `person(genealogy_id, generation)` 建复合索引，加速统计。  

**10. 索引性能对比设计**  
- 准备通过执行计划对比有无索引时 “查询某曾祖父的所有曾孙” 的时间。  
- 曾孙查询需要通过递归或自连接：从指定 person_id 开始，向下找子代→孙代→曾孙代。可用递归 CTE 或多次 JOIN。建立与不建索引（删除索引后再测试）两种情况下，记录执行时间并 EXPLAIN 分析。

### 第五阶段：模拟数据生成

**11. 编写数据生成脚本**  
目标：生成至少 10 个族谱，总计 ≥100,000 人，其中一个族谱 ≥50,000 人，并保证至少 30 代传承。  
- 可以用 Python 脚本连接数据库，使用 Faker 生成姓名，构造家族树算法：  
  - 对每个族谱，从一个祖先开始，逐代生成子女，控制每代人数，确保人口增长到目标规模。  
  - 婚姻：每代中随机配对男女组成家庭，生育子女。  
  - 辈分自动计算。  
  - 生卒年：合理范围，父代比子代大约 20~40 岁，死亡年龄随机（平均寿命可设定 60~80）。  
- 数据写入 CSV 文件，再 LOAD DATA 导入，或者直接逐批 INSERT。由于数据量大，建议先生成 CSV，用 `LOAD DATA LOCAL INFILE` 快速导入。  
- 要求：每人至少有一个亲缘关系（配偶或子女或父母），族谱内部形成连通图。  

**12. 实现导入导出**  
- 导入：编写 `LOAD DATA` 命令脚本，指定 CSV 文件路径、字段分隔符等，一次性将 member 数据灌入。记录执行时间。  
- 导出：演示导出某个族谱分支的备份，例如用 `SELECT ... INTO OUTFILE '/tmp/branch.csv'` 导出符合条件的成员信息。

### 第六阶段：核心 SQL 查询编写与测试

**13. 基本查询：给定成员ID，查配偶及所有子女**  
- 思路：从 family 表找出该成员作为 husband 或 wife 的家庭，得到 spouse，再从 parent_child 结合 family 找到所有子女。  
- 注意可能多个家庭（一夫多妻/再婚），需 UNION 配偶。  

**14. 递归查询：向上追溯所有祖先**  
- 用 Recursive CTE：起始为给定 member_id，递归检索 father 和 mother（通过 family 表找到该人出生时的家庭，得到 husband_id 和 wife_id 作为父母）。  
- 递归条件：`JOIN family ON (family_id = 生身家庭) … UNION ALL …`。实现时需要确认 person 记录出生家庭，可以在 person 表添加一个 birth_family_id 字段指向自己出生的家庭，简化递归。或者设计时 person 表中增加 father_id 和 mother_id 冗余字段，直接递归。但这会引入冗余，但在 3NF 允许性能权衡。考虑到演示方便，建议在 person 表增加 `birth_family_id` 外键指向 family。这样递归 CTE 能直接用。  

**15. 统计分析：平均寿命最长的一代人**  
- 寿命 = death_year - birth_year（过滤死亡年份不为空）。  
- 利用 `generation` 字段分组，计算 AVG(寿命)，排序取 TOP 1。显示该辈分信息。  

**16. 查询所有年龄 >50 且无配偶的男性**  
- 假设当前年份为 2026，则出生年份 < 1976。无配偶判断：该 member 作为 husband_id 在 family 表中无记录（或者 wife 为 null 的情况）。要注意如果 wife 死亡也算有配偶。用 NOT EXISTS 子查询排除在 family 中作为丈夫的所有人。  

**17. 找出出生年份早于该辈分平均出生年份的成员**  
- 首先用子查询/窗口函数计算每代人的平均出生年份。  
- 然后外查询筛选出生年份 < 该平均出生年份。
